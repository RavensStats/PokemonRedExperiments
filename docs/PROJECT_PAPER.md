# Reinforcement Learning for Pokémon Red: Environment Design, Training Methods, and Orchestrated Sweeps

## Abstract

This project studies how reinforcement learning can be applied to the long-horizon, partially observed task of playing *Pokémon Red* through a Game Boy emulator. The codebase combines a PyBoy-backed Gymnasium environment, a Stable-Baselines3 Proximal Policy Optimization (PPO) trainer, and a sweep orchestrator that manages many seeded runs while preserving resumability and post-evaluation automation. The central design idea is to replace brittle, frame-only novelty mechanisms with a structured state representation built from pixels, memory-derived game variables, and coordinate-based exploration. This paper explains the system architecture, the reward shaping logic, the training and logging pipeline, and the orchestration strategy used to run comparative sweeps over multiple configurations. It also motivates the method choices in relation to standard reinforcement learning practice and the broader literature on deep RL and exploration [1,2,3].

## 1. Introduction

Training an agent to play *Pokémon Red* is a useful stress test for reinforcement learning because the task combines sparse long-term objectives, partial observability, stochastic combat, and a large action space of temporally extended button presses. The agent must learn not only how to move and battle, but also how to navigate a world map, recover from setbacks, and make progress toward badges and story events. These challenges resemble the difficulties discussed in classic deep RL work: temporal credit assignment, sparse rewards, and the need for stable policy optimization over high-dimensional observations [1,2].

The project is best understood as a systems problem layered on top of a learning problem. A policy gradient algorithm alone is not enough if the environment interface is weak, if the reward signal is too sparse to guide exploration, or if experiments cannot be reproduced after an interruption. For that reason, the repository spends substantial effort on emulator integration, logging, checkpointing, sweep management, and post-run evaluation. In other words, the project is not only about training one model, but about making a family of experiments operationally tractable.

The repository implements two generations of the project. The older `baselines/` code path uses a frame-novelty style approach with monolithic image observations. The newer `v2/` path is the primary system and is the focus of this paper. V2 uses coordinate-based exploration, a dict observation space that combines pixels with structured RAM-derived features, and a cleaner reward design centered on milestone progress [4]. In practice, this design is intended to make learning more interpretable and more compatible with batch experiment management.

The project is not only about a single training run. It also includes reproducible experiment automation: sweeps over many random seeds, ranking and summarization scripts, checkpoint selection, and robustness evaluations. The current orchestrator design explicitly treats a sweep as a sequence of named runs with metadata, logs, and exit-code markers so that interrupted experiments can be resumed safely. This choice reflects a pragmatic assumption: in a long-running emulator-based RL setting, infrastructure failures are normal, so reproducibility depends as much on orchestration as on the learning algorithm.

## 2. System Overview

At a high level, each training run consists of three layers. First, `v2/baseline_fast_v2.py` configures the learning experiment and launches Stable-Baselines3 PPO. Second, `v2/red_gym_env_v2.py` exposes the emulator as a Gymnasium environment with structured observations and shaped rewards. Third, callbacks such as `v2/tensorboard_callback.py` and checkpoint saving logic record metrics and model snapshots. A sweep script or orchestrator then creates many such runs and summarizes them afterward [4].

The data flow is intentionally explicit. The emulator emits game state in two forms: what is visible on screen and what is stored in memory. The environment converts those sources into a learning-ready observation, the trainer maps observations to actions through PPO, and the callback stack records both training dynamics and game progress. This separation makes the code easier to inspect because each stage has one responsibility. It also makes it easier to diagnose failure modes. If learning looks poor, one can inspect the reward function. If the policy never improves, one can inspect the observations. If training crashes, one can inspect the run metadata and logs.

The emulator interface is built on PyBoy, which loads a Pokémon Red ROM and a saved state file to initialize the agent from a consistent starting point. The environment reads memory addresses for position, party state, badges, and event flags, then converts these values into an observation dictionary. The observation includes screen pixels, health, level-related features, badge bits, event bits, a local crop of the stitched global map, and a short history of recent actions [4].

This design is deliberately hybrid. Pixels provide visual information about the world, while RAM-derived signals expose latent game state that would otherwise be difficult to infer from raw frames alone. In contrast to a fully image-based setup, the dict observation allows the policy network to process heterogeneous modalities with separate feature extractors. That choice is especially valuable in a partially observed game where a large fraction of the useful state is encoded in internal game memory rather than on-screen graphics.

This project also distinguishes between model quality and experiment quality. A strong checkpoint is not very useful if it cannot be recovered later, compared across seeds, or re-evaluated under perturbations. The repository therefore treats metadata as a first-class artifact. Each run stores its command line, its exit code, its TensorBoard logs, and its final checkpoint path. That makes the experimental record auditable rather than implicit.

## 3. Environment Design and Reward Shaping

The core environment in `v2/red_gym_env_v2.py` is responsible for translating button presses into learning signals. The action space is discrete and corresponds to Game Boy inputs such as directional movement, A, B, and START. Each action is executed over multiple emulator ticks so that the agent experiences a temporally extended control effect rather than a single instantaneous button tap. This matches the physical semantics of controller input and makes the action space more realistic for Pokémon navigation and battle behavior.

The observation space is a Gymnasium `Dict` with several components. The pixel component captures local visual context. The `health`, `level`, `badges`, and `events` components summarize internal game status derived from RAM. The `map` component reflects exploration through a stitched global map representation. Finally, `recent_actions` supplies short-term action context. This structure is useful for PPO because it lets a multi-input policy learn separate representations for each modality before combining them in a shared latent space [1,3].

The reward function is one of the most important parts of the project. Instead of awarding only terminal success, the environment computes a progress vector and returns the change in its total value at each step. The components include event progress, healing, badge acquisition, exploration, opponent damage, penalties for stagnation, penalties for overmatched battles, and milestone-based game progress [4]. This is a dense reward shaping strategy, and it follows a common reinforcement learning principle: if the true goal is far away, intermediate signals should reflect useful subgoals that correlate with long-term success [2].

The reasoning behind this shaping is practical. In a game like Pokémon, a purely sparse objective such as “finish the game” is too delayed to support efficient policy improvement. The agent may spend millions of steps wandering without receiving a meaningful update signal. Reward shaping addresses that issue by revealing smaller achievements that correspond to viable progress. Badges, events, exploration coverage, and battle outcomes all provide partial evidence that the policy is moving toward long-horizon competence. At the same time, the design keeps the signal grounded in the actual game world rather than in an arbitrary proxy task.

The design has several practical consequences. First, exploration is measured by unique coordinates rather than by frame novelty. This makes the signal cheaper to compute and more semantically meaningful because Pokémon is fundamentally a spatial navigation task. Second, the `game_progress` and `event` components track maxima, which prevents the agent from losing progress after moving away from a location or state. Third, the combination of healing, damage, and battle-level shaping helps the agent learn local tactics without waiting for a badge or story event to arrive. The resulting reward is still shaped, but it is aligned more closely with actual gameplay objectives than a generic novelty bonus.

The coordinate-based exploration model is especially important. A frame-novelty signal can be fooled by transient animation, combat effects, or UI changes that are visually distinct but strategically irrelevant. By contrast, unique coordinate counting measures where the agent actually went. That matters in a map-based RPG, where visiting new areas is the mechanism by which the player unlocks items, battles, and story progression. The resulting exploration map is also easier to interpret by humans, which improves debugging and analysis.

The stitched global map is another important design choice. Instead of treating the world as an undifferentiated pixel field, the environment maps local coordinates into a global canvas derived from known map rectangles. This supports an exploration percentage metric and gives the agent a persistent notion of where it has been. The map representation is filtered by a valid-tile mask so that coverage statistics ignore padding and empty canvas regions [4].

## 4. Learning Algorithm and Training Loop

The main training script uses Proximal Policy Optimization, a widely used on-policy algorithm introduced by Schulman et al. [1]. PPO is a sensible choice for this domain because it is comparatively stable, requires less tuning than many off-policy alternatives, and works well with vectorized environments. The project does not attempt to solve *Pokémon Red* with an exotic custom optimizer; instead it relies on a robust general-purpose policy gradient method combined with domain-specific state and reward design.

The trainer runs multiple emulator workers using `SubprocVecEnv`, which increases sample throughput by collecting experience in parallel across CPU processes. Each worker creates its own emulator instance and contributes trajectories to the shared PPO update. This is especially important because emulator stepping is relatively expensive, and a single environment would underutilize the host machine. The resulting architecture follows the standard deep RL pattern of parallel rollouts feeding a centralized policy update [2,3].

The training pipeline also uses callbacks. A checkpoint callback saves model snapshots at fixed intervals, and a tensorboard callback records scalar summaries, histograms, and exploration imagery. This separation of concerns is deliberate: the training loop handles optimization, while the callbacks handle observability and artifact production. That makes later sweep analysis possible without changing the learning code. It also provides a natural basis for ranking runs by their final badge count, events completed, exploration coverage, or highest level reached.

The training hyperparameters reflect a balance between sample efficiency and runtime stability. The code uses vectorized environments, a moderate batch size, a small number of epochs, and a discount factor that values long-horizon progress without making immediate rewards irrelevant. These choices are consistent with PPO practice in complex control tasks: large enough to learn from many parallel trajectories, but conservative enough to avoid unstable updates. The exact values are not the central contribution of the project, but their selection shows an engineering preference for controlled, repeatable training over aggressive tuning.

Another practical choice is the use of saved emulator states for initialization. Starting from a consistent state shortens the time to useful behavior and removes the need to relearn the early game introduction on every run. That matters for sweep experiments because it reduces variance and makes differences between seeds more informative. The goal is not to train an agent to boot the game; the goal is to study policy learning after the environment has reached a meaningful starting point.

## 5. Logging, Summaries, and Evaluation

The project’s logging strategy is designed around reproducibility and post hoc analysis. Each run writes TensorBoard event files, stdout logs, checkpoints, and a metadata record of the exact command used. The summary script then reads final scalars from the event files and writes a `summary.csv`. This allows the project to compare seeds and configurations consistently after a sweep finishes.

The evaluation pipeline extends beyond training metrics. Two robustness evaluations are used after the best checkpoint is selected: input-jitter evaluation and perception-noise evaluation. Input jitter perturbs the control stream, while perception noise perturbs the observation stream. These tests are useful because they ask whether the policy is genuinely robust or merely overfit to the precise training interface. In long-horizon RL tasks, robustness checks are especially valuable because brittle policies may score well in training but fail when small perturbations are introduced.

The evaluation scripts also sanitize JSON payloads before writing results, which matters on Windows where path objects and nested structures can cause serialization errors if they are not converted to plain strings. This is a small but important example of a broader engineering theme in the project: practical RL systems often fail for mundane infrastructure reasons, so the evaluation stack must be defensive rather than assumed correct.

These evaluations also reflect a broader methodological choice: the paper is not only concerned with average return during training, but with behavior under controlled distribution shift. If a policy only succeeds when the emulator, timing, and observation stack are perfectly clean, then its practical value is limited. Jitter and noise tests probe a policy’s tolerance to perturbations that may arise from emulator variation, rendering differences, or real-world latency. Even though this project is still entirely within simulation, the robustness tests help separate memorization from usable skill.

The summarization workflow is similarly important. A sweep can contain many runs, each with multiple TensorBoard metrics, checkpoints, and logs. Rather than manually inspecting every run, the scripts aggregate metrics into CSV form. This allows the project to compare configurations systematically, identify the best checkpoint from a family of runs, and then apply robustness tests only to the selected model. That pipeline turns a large, noisy experimental space into a manageable set of decisions.

## 6. Orchestration and Experimental Design

The most recent orchestration logic is implemented in `scripts/run_compare_four_configs_round_robin_v2.py`, which coordinates sweeps over multiple configurations and random seeds. The orchestrator runs one job at a time in a round-robin order across configurations, writes per-run metadata, captures logs, and stops on failure so that the user can inspect the problem before proceeding [5]. It also records exit codes in `exit_code.txt`, which makes the entire sweep resumable. If a run has already completed successfully, the orchestrator skips it when resumed.

This design solves a concrete experimental problem. When comparing multiple configurations, one wants fairness across seeds, deterministic bookkeeping, and a way to pause or recover after a crash. A round-robin scheduler reduces the chance that one configuration monopolizes resources or benefits from a favorable time window. The metadata files ensure that each run can be traced back to its exact command-line arguments, which is essential when a sweep has multiple modes or reward settings. The conservative stop-on-failure policy is also reasonable: a native crash can indicate a GPU, emulator, or driver issue, and continuing blindly could waste many hours of compute.

The orchestrator’s post-evaluation step is also conceptually important. It ensures that robustness tests run only after all training runs have finished successfully. This reflects good experimental discipline: first establish the training result, then measure how stable the best model is under perturbation. The pipeline therefore separates training, selection, and evaluation into distinct phases rather than blending them into one long uncontrolled script.

There is also a fairness reason for this structure. When comparing several configurations, one should avoid letting a partial result from one configuration influence another. A round-robin schedule keeps the runs interleaved, reducing the chance that hardware or system drift correlates with a particular method. The configuration order is therefore not merely an implementation detail; it is part of the experimental design.

The resume logic matters because long sweeps are rarely uninterrupted. Power loss, emulator crashes, driver failures, and manual interruption all occur in real workflows. By writing run-level metadata and exit codes, the orchestrator creates a recoverable state machine. That is a simple idea, but it is critical for scaling up from toy experiments to real comparative studies.

In the specific 20-run comparison used in this workspace, the orchestrator also served as a guardrail against argument drift. The training command is assembled centrally so that all configurations share the same base hyperparameters, while only the discovered-event options vary across modes. This reduces the risk of accidentally comparing runs that differ in more than one experimental factor.

## 7. Why These Methods Make Sense

The project’s methodology is a compromise between general reinforcement learning theory and the realities of emulator-based game control. In theory, one could attempt to learn directly from raw pixels and sparse game completion rewards. In practice, this would be sample-inefficient and difficult to debug. The project instead uses structured state, reward shaping, and carefully managed parallelism.

That compromise is appropriate because the scientific question is not whether an arbitrary neural network can fit one specific gameplay trace. The question is whether a policy can learn broadly useful behavior in a complex sequential environment. To support that question, the system reduces avoidable sources of difficulty without removing the game’s essential challenges. The agent still needs to navigate, battle, explore, and plan; it simply does so with cleaner inputs and a more informative training signal.

From an RL perspective, the main ideas are standard but well applied. PPO provides a stable baseline [1]. Observation engineering reduces partial observability by surfacing internal game state. Reward shaping provides gradient-like intermediate feedback where the natural terminal objective is too sparse [2]. Multiple subprocess environments increase throughput and lower wall-clock training time [3]. Checkpointing and summaries make long training runs inspectable and interruptible. The overall system therefore reflects a mature engineering interpretation of RL research: algorithm choice matters, but environment design and experimental hygiene matter just as much.

The project also highlights the distinction between learning dynamics and evaluation dynamics. A training policy may optimize one reward landscape, but the real question is whether its best checkpoints generalize when small perturbations are introduced. That is why the post-evaluation scripts are not an afterthought. They are part of the methodology. Robustness is treated as a property that should be measured after training, not inferred from the training curve alone.

The project also illustrates an important lesson from applied deep RL. A “better” policy is often not the result of a single novel trick, but of a collection of aligned design decisions. Coordinate-based exploration is more meaningful than generic novelty for a map-based game. Dict observations are more suitable than a single composite image when the environment naturally exposes heterogeneous state. A resumable orchestrator is more useful than an ad hoc batch script when runs can last many hours and fail unpredictably. These choices improve the odds that optimization effort is spent on learning rather than on compensating for avoidable infrastructure problems.

The same lesson applies to reproducibility. If two methods are compared but one of them is harder to restart, summarize, or evaluate, then the comparison is biased by process friction rather than model quality. The orchestration and logging stack in this repository is therefore part of the experimental method, not merely a convenience layer.

## 8. Limitations and Future Work

Several limitations remain. First, reward shaping can bias the agent toward proxy objectives if the shaped terms are not perfectly aligned with game completion. Second, the policy still depends on emulator state and saved-state initialization, so it is not a fully “from scratch” general game-playing system. Third, the current orchestration logic stops on failure rather than automatically recovering, which is conservative but not maximally autonomous.

There are also modeling limitations. The policy uses structured state derived from the emulator, which is highly effective but also less general than learning solely from raw sensory input. The exploration signal is coordinate-based, which fits *Pokémon Red* well, but may not transfer directly to other tasks where the notion of “coverage” is less spatially grounded. In addition, reward shaping introduces domain knowledge that improves trainability but complicates claims about end-to-end discovery.

Future work could improve robustness in several directions. The reward function could be validated more systematically against downstream task success. The orchestrator could be extended with automatic retry logic for specific classes of failures. Additional evaluation protocols could include ablation studies on the observation components, such as removing the map crop or RAM-derived event bits to quantify their contribution. A more extensive study could also compare the V2 coordinate-based exploration mechanism to the older KNN novelty approach from the baseline code path.

Another useful extension would be a formal ablation table comparing the role of each reward term. For example, one could remove exploration reward, remove game-progress shaping, or remove the event bits from the observation and then compare both final performance and robustness to perturbation. That would help determine which parts of the method are essential and which are merely helpful implementation details.

## 9. Conclusion

This repository demonstrates a practical approach to training reinforcement learning agents for a complex emulator-based game. Its main contribution is not a new RL algorithm, but a carefully engineered system: a structured environment, shaped rewards, parallel rollout collection, checkpointing, summary statistics, and a resumable multi-configuration sweep orchestrator. Together these choices make the project reproducible, debuggable, and suitable for comparative experimentation.

The paper’s larger argument is that successful applied RL depends on the entire pipeline, not only the optimizer. The environment must reveal useful state, the reward must encode progress, the experiment manager must handle interruptions, and the evaluation stack must probe robustness rather than only nominal performance. In that sense, the project is a case study in how to make a difficult sequential decision problem manageable without stripping away its core complexity.

The broader lesson is that successful applied RL depends on matching method to domain. For *Pokémon Red*, that means combining pixel inputs with memory-derived state, using a reward function that exposes progress along meaningful subgoals, and wrapping the entire process in an experiment pipeline that can survive interruptions. In that sense, the project is a good example of how reinforcement learning research becomes effective software engineering.
